# Username Enumeration via Subtly Different Responses

**Lab:** [Username enumeration via subtly different responses](https://portswigger.net/web-security/authentication/password-based/lab-username-enumeration-via-subtly-different-responses) — PortSwigger Web Security Academy
**Category:** Authentication — Password-Based Login
**Difficulty:** Practitioner

## Problem

The login page returns a generic `Invalid username or password.` error for any failed login attempt, which is meant to prevent an attacker from telling a bad username apart from a bad password. However, the error message is not generated identically for every case. The goal is to find a username the application reveals as valid through this inconsistency, brute-force that user's password from a candidate wordlist, and access their account page.

Wordlists provided by the lab:
- [Candidate usernames](https://portswigger.net/web-security/authentication/auth-lab-usernames)
- [Candidate passwords](https://portswigger.net/web-security/authentication/auth-lab-passwords)

## Discovery / Exploitation

A generic error message is supposed to make invalid-username and invalid-password responses indistinguishable. In practice, the error message is often generated by different code paths depending on *why* the login failed (unknown username vs. known username/wrong password), and small inconsistencies — a different HTTP status code, a different response length, a stray character, different response timing — leak which path was taken.

Here the inconsistency is a literal typo: for one specific username, the error message has a trailing space instead of a period at the end — `Invalid username or password ` vs. `Invalid username or password.`. That's a strong signal the application is treating that username differently internally, i.e. it exists.

**Steps taken (Burp Suite):**

1. Submitted an invalid username and password through the login form with Burp's proxy running, intercepting the `POST /login` request.
2. Sent the request to Burp Intruder. The `username` parameter was auto-marked as the payload position.
3. Under **Payloads**, selected the *Simple list* payload type and loaded the candidate usernames wordlist.
4. Under **Settings → Grep - Extract**, added a new extraction by highlighting the `Invalid username or password.` text in a sample response — Burp auto-configured the extraction rule from the highlighted text.
5. Ran the attack. Burp's results grid now showed an extra column with the extracted error text for every response.
6. Sorted/scanned that column across all requests — one response stood out: same wording, but with a trailing space instead of a period. That row's `username` payload is the valid, enumerated username.
7. Went back to Intruder, fixed `username` to the identified value, and moved the payload position to `password`:
   `username=identified-user&password=§invalid-password§`
8. Replaced the payload list with the candidate passwords wordlist and ran the attack.
9. Sorted by HTTP status code — one request returned `302 Found` (a redirect, meaning successful login) instead of the `200` every failed attempt returned. That payload is the correct password.
10. Logged in with the identified username/password pair and loaded the account page — lab solved.

## Proof of Concept

**Phase 1 — enumerate the username (Burp Intruder, Sniper attack):**

- Target: `POST /login`
- Payload position: `username=§payload§&password=invalid`
- Payload type: Simple list → candidate usernames
- Grep - Extract: capture the error message text from the response body
- Result: every row returns `Invalid username or password.` except one, which returns `Invalid username or password ` (trailing space, no period) — that row's payload is the valid username.

**Phase 2 — brute-force the password (Burp Intruder, Sniper attack):**

- Target: `POST /login`
- Payload position: `username=<identified-user>&password=§payload§`
- Payload type: Simple list → candidate passwords
- Column to sort by: HTTP status code / response length
- Result: one request returns `302` (redirect to the account page) instead of `200` — that payload is the correct password.

**Phase 3 — log in:**

- Submit `username=<identified-user>&password=<identified-password>` via the normal login form.
- Account page loads — lab solved.

## Remediation

- Return byte-for-byte identical error messages, status codes, and response times for "unknown username" and "known username, wrong password" cases. Even a single stray character (like a trailing space vs. a period) is enough to leak account existence at scale via automated tools.
- Avoid branching error-generation logic by failure reason; generate the generic error from a single code path regardless of which check failed.
- Rate-limit and/or lock out login attempts per username and per IP to make large wordlist attacks impractical even if a timing/response difference exists.
- Consider CAPTCHA or progressive delays after repeated failures, and alert on abnormal volumes of login attempts against a single account or from a single source.
