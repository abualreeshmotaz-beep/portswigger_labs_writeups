# DOM XSS in `document.write` Sink Using Source `location.search`

**Lab:** PortSwigger Web Security Academy — Cross-Site Scripting
**Difficulty:** Apprentice
**Category:** DOM-based XSS

---

## Problem

The lab's search query tracking functionality contains a DOM-based XSS vulnerability. The client-side JavaScript reads user-controlled data directly from `location.search` (the URL query string) and passes it, unsanitized, into `document.write()`. Since `location.search` is fully attacker-controlled via the URL, and `document.write` writes raw markup into the page, this creates a client-side injection point that never touches the server.

**Source:** `location.search`
**Sink:** `document.write()`

The goal is to perform a cross-site scripting attack that calls the `alert` function.

---

## Discovery / Exploitation

1. Entered a random alphanumeric canary string into the search box and submitted the search.
2. Right-clicked the reflected value in the rendered page and chose "Inspect" to view its exact position in the DOM.
3. Observed that the canary string was placed inside an `<img>` tag's `src` attribute, generated by the following pattern in the page's inline script:
   ```javascript
   function trackSearch(query) {
       document.write('<img src="/resources/images/tracker.gif?searchTerms=' + query + '">');
   }
   var query = (new URLSearchParams(window.location.search)).get('search');
   if (query) {
       trackSearch(query);
   }
   ```
4. Since the value lands inside an existing `src="..."` attribute with no encoding, the attribute can be closed early and new markup injected right after it.

---

## Proof of Concept

**Payload used in the search box:**
```html
"><svg onload=alert(1)>
```

**Resulting injected markup:**
```html
<img src="/resources/images/tracker.gif?searchTerms=""><svg onload=alert(1)>">
```

**Steps:**
1. Enter the payload above into the search box.
2. Click "Search".
3. The closing `">` breaks out of the `src` attribute and the `<img>` tag itself; the injected `<svg onload=alert(1)>` element is then parsed as new markup.
4. As soon as the `<svg>` element renders, its `onload` event handler fires, triggering `alert(1)`.

**Resulting URL:**
```
https://YOUR-LAB-ID.web-security-academy.net/?search="><svg onload=alert(1)>
```

---

## Remediation

- **Avoid `document.write` with untrusted data:** Never pass user-controlled input (especially from `location.search`, `location.hash`, `document.referrer`, etc.) into `document.write()`. Prefer safer DOM manipulation methods.
- **Contextual output encoding:** If dynamic values must be written into an HTML attribute, HTML-attribute-encode the value first (encoding `"`, `<`, `>`, etc.) so it cannot break out of the attribute or tag.
- **Content Security Policy (CSP):** A strict CSP can prevent inline event handlers (like `onload=`) from executing, mitigating this class of attribute-breakout XSS even if encoding is missed somewhere.
- **Client-side source auditing:** Treat all `location.*` and other client-controlled sources as untrusted input, on par with server-side untrusted input, and trace their flow to every sink they reach.
